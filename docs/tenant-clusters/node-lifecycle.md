# 节点生命周期

## 概述

本文档描述 NVKE 租户集群中工作节点的常规生命周期控制：

- **自动供应**使节点池向其期望数量收敛。
- **自动模式**将已弃用 NodeSet 中的节点标记为待回收，但不会替换它们。
- **外部故障修复系统**决定何时可以执行感知工作负载的封锁（cordon）、排空（drain）和终止。
- **运维人员**可在需要时手动重启或终止单个节点。

> **重要：** NVKE 不负责决定何时可以中断租户工作负载。封锁、排空和工作节点 SLO 策略必须由租户 SRE 团队和/或与你的工作负载调度器集成的故障修复系统（如 [NVSentinel](https://github.com/NVIDIA/NVSentinel)）处理。NVKE 提供生命周期 API；策略执行由你负责。

## 自动供应

自动供应是 NVKE 对节点池的期望数量协调，**不是**由工作负载驱动的自动扩缩容。

节点池的 `desiredNodeCount` 是目标节点数。NVKE 控制器持续将期望数量与该池的节点记录进行比较。当池内节点数低于期望数量时，控制器创建待处理节点记录，并在有匹配的基础设施容量时进行供应。若无可用容量，替换操作会等待容量恢复。

“匹配容量”不仅仅指空闲的物理节点。控制器必须找到满足节点池要求的容量，包括实例类型、硬件特性、允许的子网放置和可用 IP 空间。即使存在合适的硬件，如果配置的子网或 IP 分配已耗尽，节点池仍可能保持待处理状态。

当实际数量超过期望数量时，自动供应**不会**自动移除健康的在用节点。缩容仍需显式终止流程。

自动供应使节点在重启、修复、回收或手动终止后基本无需人工干预即可完成替换。如果节点池期望数量保持不变，被终止的工作节点会在有可用容量时被替换。

## 调整节点池的期望数量

当节点池的预期稳态规模发生变化时，使用期望数量。不要将其用作工作负载自动扩缩器；它应反映资源治理或运维人员的明确决策。

### 增加期望数量

使用 `nvkectl` 设置更高的数量：

```bash
nvkectl patch nodepool <POOL_NAME> --cluster <WORKLOAD_CLUSTER> --patch 'desiredNodeCount: <COUNT>'
```

容量可用时节点会自动供应。节点列表（`GET /api/nodes?nodePoolID=<NODE_POOL_ID>`）中的待处理节点表示正在等待匹配资源的期望容量。

### 减少期望数量

使用 `nvkectl` 设置更低的数量：

```bash
nvkectl patch nodepool <POOL_NAME> --cluster <WORKLOAD_CLUSTER> --patch 'desiredNodeCount: <COUNT>'
```

NVKE 不会仅因期望数量减少就自动终止健康的在用节点。这可能导致池内节点数多于期望值。要完成缩容，请使用[终止节点](#终止节点)终止选定的节点。

> **警告：** 仅在租户中断策略允许时终止活跃工作节点。优先选择维护窗口或未运行租户工作负载的节点。

## 自动模式回收

自动模式会分批将已弃用 NodeSet 中的工作节点标记为 `nvke.nvidia.com/NeedsRecycle` 条件。NVKE 不会封锁、排空或终止被标记的节点。由运维人员或配置为响应该条件的故障修复系统决定每个节点何时可以排空和终止，随后 NVKE 会供应其替换节点。

## 重启节点

如果需要重启节点，请使用以下方法之一：

1. **通过 [NVSentinel](https://github.com/NVIDIA/NVSentinel)** — 在节点被回收或修复时首选，因为这使 NVSentinel 有机会在重启前应用感知工作负载的封锁和排空策略。
2. **通过 NVKE API 或 `nvkectl`** — 预览版中不可用。

对于新的标签驱动工作节点重启，控制器首先通过节点代理请求软重启。它每 10 秒轮询一次启动变化，或按配置更快轮询。如果代理响应丢失，控制器会等待，因为重启可能已在进行中。如果在验证截止时间前未出现启动变化，控制器通过基础设施提供商请求硬重启。截止时间默认为调度尝试完成后 30 分钟。`NODE_REBOOT_INITIAL_TIMEOUT` 可以缩短该窗口，但不能将软验证延长至超过 30 分钟。后续尝试使用硬重启，直到启动验证成功。

升级前，控制器会再次读取节点。新的启动 ID 可防止重复重启。移除重启标签、出现删除时间戳或终止标签会取消升级。此流程中控制器不会解除节点封锁。你的故障修复系统控制工作负载恢复和解除封锁。

此变更不保留活跃重启工作流的重放兼容性。在控制器升级前，取消活跃的重启工作流。等待取消和清理完成。升级后，为仍需恢复的节点启动新的重启工作流。

## 终止节点

手动终止节点应是例外情况。当节点被回收或修复时，优先使用 [NVSentinel](https://github.com/NVIDIA/NVSentinel) 故障修复流程——该路径会在终止前应用感知工作负载的策略。

如需自行终止节点，请通过 NVKE API 使用 `curl -X DELETE "<API_URL>/api/nodes/<NODE_ID>"` 删除，如[替换节点](../workload-clusters/node-pools.md#replace-a-node)所述。如果 NodePool 期望数量保持不变，被终止的节点会在有匹配容量时自动替换。`nvkectl` 没有对应命令。

如果节点仍存在于 Kubernetes 中但已从控制器中消失，则它是仅存在于 Kubernetes 的僵尸节点。请手动移除：

```bash
kubectl delete node <node-name>
```

## 节点生命周期故障排查

**节点卡在 Pending 状态：**

- 检查控制器日志中的容量分配错误。
- 验证配置的子网有可用 IP 空间。
- 确认基础设施提供商（NICo）有匹配容量。

**节点供应后未加入：**

- 检查节点上的 `nvke-agent`：`systemctl status nvke-agent`
- 验证管理集群到节点端口 15005（gRPC）的网络连通性
- 在 Temporal UI 中检查控制器的工作流日志（在管理集群中端口转发 `temporal-web`）

**节点在 Kubernetes 中显示 Ready 但 NVKE 认为其不健康：**

- NVKE 在自己的数据库中跟踪节点状态。使用 `GET /api/nodes/<NODE_ID>` 检查节点的记录状态。
- 控制器会将节点的 Kubernetes 状态与 NVKE 记录进行协调；如有差异，请检查控制器日志。
